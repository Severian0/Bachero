# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Bachero: council fleet vehicles carry phones that detect potholes; Supabase clusters detections into potholes; a Next.js dashboard plans and dispatches repair routes; a login-free crew page closes the loop. Hackathon MVP. **Read `docs/ARCHITECTURE.md` first** — it is the spec, including request/response shapes for every endpoint and the demo script. Do not re-derive it here.

## Layout

- `docs/ARCHITECTURE.md` — the spec (data, endpoints, demo script).
- `docs/design/DESIGN.md` — the design system; `docs/design/bachero-console.html` is the rendered console mockup (Claude Design export, open in a browser) and `docs/design/mockup/` holds its readable markup, logic and base stylesheet. `docs/` is documentation and reference only; no application code.
- `supabase/migrations/20260901000000_init.sql` — the whole schema: tables, the two triggers, read-model views, storage bucket, realtime publication, demo RLS, demo seed. One file; read it before touching data.
- `dashboard/` — Next.js 16 (App Router, `src/`, Tailwind 4, TypeScript). Hosts the dashboard UI, the two API route handlers, and the crew page.
- `sensor/` — Flutter app. Not yet bootstrapped (`flutter create .` per `sensor/README.md`); `lib/config.dart` holds the seeded device/vehicle UUIDs and detector constants.

## Commands

Dashboard (run from `dashboard/`):

```sh
npm run dev      # http://localhost:3000
npm run build
npm run lint     # eslint (flat config)

```

Database:

```sh
supabase db push                    # apply migrations to the linked project
supabase db reset                   # local: drop + reapply (includes the seed block)
```

Env: copy `dashboard/.env.example` to `dashboard/.env.local`. `NEXT_PUBLIC_SUPABASE_*` are used by the browser client in `src/lib/supabase.ts`; `RESEND_API_KEY` and `OSRM_BASE_URL` are server-only.

## Data rules that will bite

- **Never read geography columns from the client.** PostgREST returns them as hex WKB. Read `potholes_map`, `repair_queue`, `latest_vehicle_positions`, `route_plans_map` — they expose `lng`/`lat`/`path_geojson`. Row types live in `dashboard/src/lib/types.ts`; keep them in sync with the views.
- **Longitude first.** EWKT is `SRID=4326;POINT(lng lat)`; GeoJSON coordinates are `[lng, lat]`; OSRM URLs are `lng,lat`. Google Maps links are the one exception (`lat,lng`).
- **Nobody inserts into `potholes`.** The `BEFORE INSERT` trigger on `detections` creates or joins a pothole (12 m radius, `v_radius_m`) and promotes `suspected → confirmed` on a second *distinct vehicle*. To make a pothole appear, insert a detection.
- **Pothole status is driven by `work_orders`.** `assigned`/`in_progress` → `scheduled`, `done` → `repaired`, via the `work_orders_sync` trigger. The only pothole status a client sets directly is `false_positive`.
- `route_plans` is `unique (crew_id, plan_date)` and `work_orders` is `unique (route_plan_id, stop_order)` — replanning the same crew/day must delete or update, not insert.
- Schema changes go in a new `supabase/migrations/<timestamp>_<name>.sql`; don't edit the init migration once it has been applied anywhere. The seed block at the bottom of it is demo-only.

## Design rules

Spec: `docs/design/DESIGN.md`. Tokens: `dashboard/src/app/globals.css`, exposed both as CSS variables and as Tailwind theme values (`bg-accent`, `text-ink-55`, `border-divider`, `font-heading`, `rounded-lg`, `shadow-sm`; the spacing multiplier is 3.4px so `p-4` = `--space-4`).

- **Tokens only.** Never hard-code a hex, font, radius or shadow in a component. Spacing is the `--space-1…8` scale (3.4px × n); no other values.
- **One accent, no status colours.** Pothole status is fill/weight/form (hollow, solid, solid with stop number, faded neutral); severity is size and the segmented bar; priority is the numeral. No red/amber/green. Colour never carries information without a label.
- **Where the notes and the mockup disagree, the mockup wins** (Inter, rounded radii, no registration marks — DESIGN.md §0 has the table). Light theme only; no dark mode.
- **Motion is 120 / 240 / 1200 ms with `--ease`** (tints / status change / vehicle interpolation). Hover states are tints, never movement. Nothing else animates.
- **Linked selection** (row ↔ pin, keyboard `↑↓ Enter Esc F`) is the core interaction; the inspector is fixed-height so hovering never shifts layout.
- **Copy:** civil-service plain English, measurement before inference ("3 vehicles, 11 passes" then "confirmed"), units on numbers, verbs with objects on buttons ("Plan route", "Dispatch to crew"), no exclamation marks.
- Build components from the mockup's `console.html` + `console.logic.js`; the mockup's `renderVals()` is the reference for pin size, fill, stroke, glow and row marker per status.

## Where things go

- Solver: `dashboard/src/app/api/plan-route/route.ts`. Greedy insertion on `priority / marginal_minutes` + 2-opt over an OSRM `/table` matrix with the depot at index 0. Keep the heuristic pure and testable; the route handler should only do I/O around it.
- Dispatch email: `dashboard/src/app/api/dispatch/route.ts` (Resend). The crew page link is primary; GMaps deep links are chunked per leg because of waypoint limits.
- Crew page: `dashboard/src/app/route/[id]/page.tsx`. Mobile-first, no auth, PATCHes `work_orders` only.
- Realtime: subscribe to `public.potholes` (all events) and `public.vehicle_positions` (INSERT). Payloads carry raw geography, so on a pothole change re-fetch that row from `potholes_map`.
- Security is intentionally absent (`demo_all` RLS policies, public storage bucket). Don't spend time hardening; do keep `authority_id` on anything new so tenancy is a policy change later.
