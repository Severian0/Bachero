# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Bachero: council fleet vehicles carry phones that detect potholes; Supabase clusters detections into potholes; a Next.js dashboard plans and dispatches repair routes; a login-free crew page closes the loop. Hackathon MVP. **Read `docs/ARCHITECTURE.md` first** — it is the spec, including request/response shapes for every endpoint and the demo script. Do not re-derive it here.

## Layout

- `docs/ARCHITECTURE.md` — the spec (data, endpoints, demo script).
- `docs/design/DESIGN.md` — the design system: tokens, components, map styling, data states, interaction, copy. `docs/design/bachero-console.html` and `docs/design/mockup/` are an earlier exploration on a retired token set, kept for the interaction model only (DESIGN.md §0 says which parts still apply). `docs/` is documentation and reference only; no application code.
- `supabase/migrations/20260901000000_init.sql` — the whole schema: tables, the two triggers, read-model views, storage bucket, realtime publication, demo RLS, demo seed. One file; read it before touching data.
- `dashboard/` — Next.js 16 (App Router, `src/`, Tailwind 4, TypeScript). Hosts the console UI, the two API route handlers, and the crew page.
  - `src/components/` — screen-level components, flat: `Console.tsx` (the shell), `Header.tsx`, `PotholeMap.tsx`, `OperationsColumn.tsx`, `RecordPanel.tsx`, `DispatchSheet.tsx`, `DetectionFrame.tsx`, `Logo.tsx`. Map internals live one level down in `src/components/console/map/` (`ConsoleMap`, `MapLayers`, `PotholePin`, `VehicleMarker`, `TrailLayer`, `RouteLayer`, `PreviewDriveLayer`, `CrosshairGuides`, `Graticule`, `ScaleBar`).
  - `src/lib/console/` — pure console logic and its tests: `store.ts` (zustand), `derive.ts`, `format.ts`, `keyboard.ts`, `area.ts`, `interpolate.ts`, `visual.ts` (the status → pin/tag/marker table), `branding.ts`.
  - `src/lib/data/` — the data source (`synthetic.ts`, `supabase.ts`, `types.ts`, `index.ts`); `src/lib/solver/` — the routing heuristic; `src/lib/map/` — the MapLibre style and its tokens.
- `sensor/` — Flutter app. Not yet bootstrapped (`flutter create .` per `sensor/README.md`); `lib/config.dart` holds the seeded device/vehicle UUIDs and detector constants.

## Commands

Dashboard (run from `dashboard/`):

```sh
npm run dev        # http://localhost:3000
npm run build
npm run lint        # eslint (flat config)
npm run typecheck  # tsc --noEmit
npm test           # vitest run
```

Database:

```sh
supabase db push                    # apply migrations to the linked project
supabase db reset                   # local: drop + reapply (includes the seed block)
```

Env: copy `dashboard/.env.example` to `dashboard/.env.local`. `NEXT_PUBLIC_SUPABASE_*` are used by the browser client in `src/lib/supabase.ts`; `RESEND_API_KEY` (optional), `DISPATCH_FROM_EMAIL` (default `onboarding@resend.dev`) and `OSRM_BASE_URL` (default `https://router.project-osrm.org`) are server-only. `NEXT_PUBLIC_CONTRACTOR_URL` (default `http://localhost:3001`) is the contractor portal's base URL, which is where the crew screens now live: both the dispatch email's crew link and this app's `/route/{id}` redirect are built from it by `src/lib/links.ts`, so it has to be reachable by the crew's phone. `NEXT_PUBLIC_APP_URL` is no longer read by anything.

## Data rules that will bite

- **Never read geography columns from the client.** PostgREST returns them as hex WKB. Read `potholes_map`, `repair_queue`, `latest_vehicle_positions`, `route_plans_map` — they expose `lng`/`lat`/`path_geojson`. Row types live in `dashboard/src/lib/types.ts`; keep them in sync with the views.
- **Longitude first.** EWKT is `SRID=4326;POINT(lng lat)`; GeoJSON coordinates are `[lng, lat]`; OSRM URLs are `lng,lat`. Google Maps links are the one exception (`lat,lng`).
- **Nobody inserts into `potholes`.** The `BEFORE INSERT` trigger on `detections` creates or joins a pothole (12 m radius, `v_radius_m`) and promotes `suspected → confirmed` on a second *distinct vehicle*. To make a pothole appear, insert a detection.
- **Pothole status is driven by `work_orders`.** `assigned`/`in_progress` → `scheduled`, `done` → `repaired`, via the `work_orders_sync` trigger. The only pothole status a client sets directly is `false_positive`.
- `route_plans` is `unique (crew_id, plan_date)` and `work_orders` is `unique (route_plan_id, stop_order)` — replanning the same crew/day must delete or update, not insert.
- Schema changes go in a new `supabase/migrations/<timestamp>_<name>.sql`; don't edit the init migration once it has been applied anywhere. The seed block at the bottom of it is demo-only.

## Design rules

Spec: `docs/design/DESIGN.md`. **`dashboard/src/app/globals.css` is canonical** — it defines every token and every shared class. The set is derived from the GOV.UK Design System: ink `--ink/--ink-2/--ink-3`; ground `--surface/--canvas/--rule/--rule-soft`; command chrome `--rail*` and the feed dots; meaning `--action` / `--committed` / `--severe` / `--closed`; focus `--focus/--focus-ink`; type `--font-ui` (Public Sans) and `--font-data` (IBM Plex Mono, tabular) at `--t-micro…--t-metric`; space `--s1…--s7` (4/8/12/16/24/32/48); radii `--r-sm/--r-md/--r-lg/--r-full`; shadows `--shadow-1/2/3`; `--ease`.

- **Tokens only, and only these tokens.** Never hard-code a hex, font, size, radius or shadow in a component, and never name a variable that is not in `globals.css` — the retired names from the earlier exploration (listed in DESIGN.md §0) no longer resolve to anything. Two files may name a literal colour: `globals.css` itself and `dashboard/src/lib/map/tokens.ts`, where MapLibre cannot read a CSS custom property.
- **Two lanes of meaning, and only two: blue is work proposed (`--action`), green is work committed to a crew (`--committed`).** `--severe` is the grade-4 severity bar and nothing else; `--closed` is repaired. Severity is size plus the 4-segment bar; priority is the numeral. No red/amber/green status ramp. Colour never carries information without a label — status is always spelled out.
- **Status visuals come from `STATUS_VISUAL` / `pinSize` / `severityFill` in `dashboard/src/lib/console/visual.ts`**, never from a value chosen at the call site. Pin sizes are 14/18/22/26px for grades 1–4.
- **Use the classes:** `.btn` with `-primary` (propose) / `-commit` (dispatch) / `-secondary` / `-quiet` / `-sm`, `.tag` with the four status variants, `.data` for any number in a column, `.micro` for uppercase labels, `.secondary` to step type back. Light theme only; no dark mode.
- **Motion is 120 / 240 / 1200 ms with `--ease`** (tints / status change / vehicle interpolation), plus the 200 ms pin scale. Hover states are tints, never movement. Nothing else animates; `prefers-reduced-motion` is honoured in `globals.css`.
- **Linked selection** (row ↔ pin, keyboard `↑↓ Enter Esc F`) is the core interaction. `Enter` opens the record; `Esc` steps back one level per press. Blocks that are loading hold their height so nothing shifts under the cursor.
- **Phones.** Below 1024px (`@media (max-width: 1023px)` in `globals.css`) the frame stacks: rail, map, then the column as a panel whose height follows `aside[data-panel]` (`queue` 50dvh, `record` 66dvh, `map` handle-only, set from the store's `panel` and `pinnedId`). Layout is CSS only; there is no JS media-query hook. Touch never links, it opens: hover handlers are pointer events gated on `pointerType !== "touch"`, and the Back button calls `closeRecord()` so the link goes with the record. `(pointer: coarse)` grows 30px controls to 38px and hides the zoom cluster; the key becomes a "Show key" toggle. Spec: `docs/superpowers/specs/2026-09-04-mobile-console-design.md`. Verify with the CDP harness described there at 390×844 and 1440×900; the desktop render must not change.
- **Copy:** civil-service plain English, measurement before inference ("3 vehicles, 11 passes" then "confirmed"), units on numbers, verbs with objects on buttons ("Plan route", "Dispatch to crew"), no exclamation marks.

## Where things go

- Solver: `dashboard/src/lib/server/planRoute.ts`, behind the thin handler at `dashboard/src/app/api/plan-route/route.ts`. Greedy insertion on `priority / marginal_minutes` + 2-opt over an OSRM `/table` matrix with the depot at index 0. The pure logic and its tests live in `src/lib/server/`; handlers only parse, inject I/O and map errors to status codes.
- Replanning a crew's day replaces that `(crew_id, plan_date)` plan: set its work orders to `cancelled`, reset each freed pothole to `confirmed` (only where no other open work order holds it — the `work_orders_sync` trigger moves potholes *into* `scheduled` but never back), then delete the work orders and the plan before inserting the new one.
- Dispatch email: `dashboard/src/lib/server/dispatch.ts`, behind `dashboard/src/app/api/dispatch/route.ts` (Resend, wrapped in a `Mailer` interface so tests never send). The crew page link is primary; GMaps deep links are chunked per leg (at most 8 waypoints) because of waypoint limits, and are the one place that is `lat,lng`. Without `RESEND_API_KEY` the plan is still published and the response says `sent: false`.
- Crew page: `dashboard/src/app/route/[id]/page.tsx`. Mobile-first, no auth, PATCHes `work_orders` only.
- Realtime: subscribe to `public.potholes` (all events) and `public.vehicle_positions` (INSERT). Payloads carry raw geography, so on a pothole change re-fetch that row from `potholes_map`.
- Security is intentionally absent (`demo_all` RLS policies, public storage bucket). Don't spend time hardening; do keep `authority_id` on anything new so tenancy is a policy change later.
- Console screen: one client screen at `dashboard/src/app/page.tsx`, which renders `dashboard/src/components/Console.tsx` and nothing else. `Console.tsx` is the only place that mounts the data source, attaches the keyboard listener, and turns store state into child props; the children take props and hold no data of their own (`DispatchSheet.tsx` is the exception — it reads and writes the planner slice of the store directly).
- Console state: `dashboard/src/lib/console/store.ts` (zustand). Everything on the screen reads from it, so the map and the column can never disagree. Derivations, formatting, keyboard, area maths and the vehicle tween are the other pure modules beside it, each with a test file. Spec: `docs/superpowers/specs/2026-09-02-console-map-design.md`.
- Route planner UI: `dashboard/src/components/DispatchSheet.tsx` — crew, mode (`manual` / `count` / `time`), stop and time budgets, service minutes, the drawn area, the plan result and the real dispatch, all in one modal. It is the only interrupting surface in the product; do not add a second.
- Data layer: `dashboard/src/lib/data/` behind `createDataSource()` in `index.ts` — the synthetic fleet by default, Supabase when `NEXT_PUBLIC_SUPABASE_URL` is set. Components never import a Supabase client.
- `planRoute()` calls `solve()` from `dashboard/src/lib/solver/heuristic.ts` with the OSRM matrix (depot at index 0); the synthetic data source already does this with a haversine matrix. Server-only helpers it shares with dispatch: `src/lib/server/supabase.ts` (`serverClient()`), `src/lib/server/wkb.ts` (`parsePointWkb`, for `crews.depot`), `src/lib/server/osrm.ts`.
